# Contributing to MadMusic

MadMusic is a private, proprietary project. Access is by invitation, and this
document is written for people who already have it.

## Setup

```bash
corepack enable
pnpm install
pnpm dev
```

Use pnpm. The lockfile is `pnpm-lock.yaml` and it is committed; a change to it
must always accompany the `package.json` change that caused it.

## The one rule

Run **`pnpm verify`** before every commit and before opening any PR.

```bash
pnpm verify   # format:check -> lint -> typecheck -> test -> build
```

GitHub Actions runs the same command on every push and pull request, and
builds releases from tags (see [docs/ci-plan.md](docs/ci-plan.md)). Nothing else will catch a
broken build for you, so this command is not optional.

If `format:check` fails, run `pnpm format`. If `lint` fails, try
`pnpm lint:fix` first, then fix the rest by hand — do not add a blanket
`eslint-disable`; if a rule is genuinely wrong for this codebase, change the
rule in `eslint.config.js` and say why in the PR.

## Branches

Work on a branch off `main`; never commit to `main` directly.

```
feat/library-scanner
fix/playback-seek-drift
chore/bump-vite
docs/architecture-notes
```

Prefixes: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `perf`.

## Commits

[Conventional Commits](https://www.conventionalcommits.org/). The subject is
imperative, lowercase, and has no trailing period.

```
feat(player): add gapless playback between queued tracks
fix(library): stop rescanning unchanged folders on startup
chore(deps): bump vite to 8.2.1
```

Scopes follow the product areas: `player`, `library`, `queue`, `search`, `sync`,
`ui`, `deps`, `build`, `docs`.

### Authorship

Every commit is authored by the repository owner and nobody else:

```
Mad Blast <81722794+MadBlast0@users.noreply.github.com>
```

**Do not add `Co-Authored-By` trailers — for AI assistants or anyone else.**
Tools that append AI attribution by default must be configured not to. MadBlast0
is the sole contributor on this repository, and the commit log should say so.

This is pinned in the repo's local git config, so an ordinary `git commit` here
already does the right thing. Do not override it with `-c user.email=...`.

## Pull requests

Open a PR even when working alone — the diff is the record of why a change
exists. Fill in the template, keep the PR to one logical change, and confirm
`pnpm verify` passed. Squash-merge into `main`.

## Code style

Formatting is Prettier's problem, not yours — do not hand-align anything.
Beyond that:

- **TypeScript, strictly.** No `any`. If a type is genuinely unknown, use
  `unknown` and narrow it.
- **Imports** use the `@/` alias for anything inside `src/`.
- **Components** are function components. Files in `src/components/ui/` are
  generated by shadcn — regenerate rather than hand-editing where practical, and
  if you must edit one, note it in the PR.
- **Comments explain why, not what.** The existing files in
  `src/components/common/` set the expected tone and density; match it.
- **Tests** live beside the code as `*.test.ts(x)` and assert user-visible
  behaviour through Testing Library queries, not implementation details.

## Rust and the Tauri shell

### Windows prerequisite: `rc.exe`

The Tauri build embeds a Windows resource (the icon and version info), which
needs **RC.EXE** from the Windows SDK. It is installed with the SDK but is
**not on `PATH` by default**, and the failure it produces names neither Tauri
nor the SDK:

```
called `Result::unwrap()` on an `Err` value:
Failed("Are you sure you have RC.EXE in your $PATH or ${RC_$TARGET} or $RC is set?")
```

Either build from a **Developer Command Prompt for VS**, which puts it on
`PATH`, or add the SDK's `x64` directory yourself:

```powershell
$env:PATH = "C:\Program Files (x86)\Windows Kits\10\bin\10.0.26100.0\x64;$env:PATH"
```

Substitute the SDK version you actually have — `ls "C:\Program Files (x86)\Windows Kits\10\bin"`
lists them. This is deliberately not pinned in `.cargo/config.toml`: the path
contains a version number that differs per machine, and committing one would
break the build for everyone whose SDK does not match.

Only the Rust build needs this. `pnpm dev`, `pnpm test` and `pnpm build` do not.

### Rules

- **Keep the Rust layer thin.** It exists for what the webview cannot do: OS
  APIs, filesystem, windowing, secure storage, native dialogs. Business
  logic and UI state belong in `src/`. If a command is doing product logic, it
  is in the wrong place.
- **Commands are a trust boundary.** Everything crossing from the frontend is
  untrusted input — validate paths, reject traversal, never interpolate a string
  into a shell. A command that takes a path and opens it is the most likely
  place this project gets a CVE.
- **Capabilities are deny-by-default in Tauri v2.** Grant the narrowest
  permission that works and comment why in the capability file. Do not widen a
  scope to make something work without saying so in the PR.
- **Errors cross the boundary as typed, serialisable values** — not stringified
  panics. Never `unwrap()` on anything reachable from a command.
- **`cargo fmt` and `cargo clippy -- -D warnings`** are expected to pass, the
  same way Prettier and ESLint are on the TypeScript side. Both are part of
  `pnpm verify`, along with `cargo test`, so there is still one command to
  remember.
- **Network tests are `#[ignore]`d.** The catalogue's live checks hit YouTube,
  so they are excluded from `pnpm verify` and run on demand:
  `cargo test --manifest-path src-tauri/Cargo.toml -- --ignored --nocapture`.
  Run them when playback, search or the home screen misbehaves — extraction
  breaking is expected maintenance, not a surprise.

## Dependencies

This project runs a deliberately conservative dependency policy, half of it
machine-enforced:

- `minimumReleaseAge: 10080` in `pnpm-workspace.yaml` makes pnpm refuse any
  package version published in the last **7 days**. This blocks the typosquat /
  hijacked-maintainer class of attack outright. Do not lower it to unblock
  yourself — wait, or pin a known-good older version.
- For **major** upgrades, prefer versions that have been out roughly **3
  months**. That is the human-judgement layer on top of the 7-day floor.
- Before adding a dependency, ask whether ~30 lines in `src/lib/` would do.
  Every dependency is permanent supply-chain surface.
- Run `pnpm audit` after any dependency change. Security pins belong in the
  `overrides` block in `pnpm-workspace.yaml`, with a comment explaining the
  advisory and when the pin can be dropped.

## Secrets

Never commit one. `.env*` is gitignored except `.env.example`; add each new
variable there with a comment and a safe placeholder. Anything prefixed `VITE_`
is compiled into the client bundle and is therefore public — treat it as such.

If a secret does land in a commit, treat it as compromised: rotate it first,
then clean the history. See [SECURITY.md](SECURITY.md).
